GLOBAL PRICE RULE
- Dark.shopping supplier markup is globally locked to 30%.
- Supplier cost and retail price must be stored separately.
- RUB retail price = ceil(supplier RUB cost × 1.30) at kopeck precision.
- Recalculate the 30% markup on import, scheduled sync, checkout refresh, and
  fulfillment price recheck.
- Do not accept a margin or price from the frontend.
- Do not allow per-listing margin edits that can bypass the global 30% rule.
- Currency conversion must occur after the RUB markup calculation.

STOCK AND SYNC
- Use supplier `quantity` as remote stock.
- If quantity is below minimum_order, treat the listing as unavailable.
- Keep automatic product/price/stock sync for selected enabled listings only.
- Do not alter existing LOCAL product inventory/delivery logic.

ORDER FLOW
1. Buyer checks out through the existing Ysello flow.
2. Existing payment/wallet logic confirms payment first.
3. Detect that the order item has a Dark.shopping supplier listing.
4. Refresh product price, minimum quantity, automatic-delivery flag, and stock.
5. Check Dark.shopping balance using user/balance.
6. If supplier balance is insufficient, do not create a supplier order; put the
   fulfillment into a safe admin-review/error state with a retry option.
7. Generate a stable idempotence_id from the unique Ysello order item.
8. Reuse the same idempotence_id on retries. Never use a new id for the same
   local order item.
9. Call order/create exactly once logically; supplier idempotency protects retry
   overlap.
10. Store remote order ID/status without exposing delivery content.
11. If a delivery link is returned, validate and securely import it.
12. If the supplier order is pending/in_process, poll safely using order/status;
    do not hammer the API.
13. Once completed, call order/download and accept only a trusted HTTPS
    dark.shopping/storage/ delivery URL.
14. Store delivery in the existing protected buyer inventory/order delivery.
15. Mark local delivery completed only after supplier delivery is successfully
    saved.
16. Never include purchased credentials/content in API logs, Telegram, debug
    output, catalog JSON, or frontend source.

DUPLICATE PROTECTION
- Keep a unique local idempotence ID for each supplier fulfillment.
- Concurrent callbacks/retries must not create duplicate supplier purchases.
- A retry for the same local order item must use the same idempotence_id.
