# Ysello 2026-09-09.1 — Telegram fixes

Based on the latest saved full build, 2026-09-08.6 (professional categories).

## Why crawler notifications appeared

VISITOR_NOTIFY_INCLUDE_BOTS defaulted to true, and an HTTP response hook deliberately sent crawler notifications. That hook has been removed. Known bots are now rejected even if an old Railway variable still says true.

## Visitor behavior

Alerts require a public Ysello page, a browser user agent, at least 35 seconds elapsed, 30 seconds visible, and a trusted pointer, keyboard, or wheel interaction. Browser automation reported through navigator.webdriver is excluded. Visible time accumulates across public page navigation. Private routes and static resources are rejected by the server. Storage failures no longer break the component. The client only records success when the server confirms it, and retries unsuccessful sends at 15-second intervals. Concurrent beacons are suppressed within one API process; successful visits retain the existing deduplication window.

These signals identify likely human engagement, not guaranteed human identity. Passive readers who never interact will not trigger an alert. Sophisticated automation can imitate browser signals. Dedupe state is in memory and resets on restart; multiple API replicas do not share it.

## Order and top-up notifications

Existing order-created, wallet-paid, crypto-confirmed, top-up-created, and proof-submitted notifications remain. Screenshot forwarding remains. Without a dedicated ORDER_TELEGRAM_BOT_TOKEN, notifications use TELEGRAM_BOT_TOKEN. Without a dedicated ORDER_TELEGRAM_CHAT_ID, they use the main selected chat. Explicit dedicated settings take precedence.

New approval and rejection alerts run after successful admin transactions. Approval reports the credited amount and current wallet balance. Notifications cannot approve payments or alter balances.

Also fixed existing TypeScript errors: nullable order results at notification call sites and screenshot Blob construction.

## Deploy

1. Copy the contents of the ZIP's ysello_085 folder over the existing repository root, preserving your real environment variables and database.
2. Commit/push the update and redeploy Railway. Deploy the matching frontend too if it is served separately. The existing Vercel proxy architecture remains unchanged.
3. In Railway keep TELEGRAM_BOT_TOKEN and TELEGRAM_CHAT_ID configured. Set VISITOR_NOTIFY_ENABLED=true, VISITOR_NOTIFY_INCLUDE_BOTS=false, and ORDER_TELEGRAM_NOTIFICATIONS_ENABLED=true. Dedicated ORDER_TELEGRAM_BOT_TOKEN and ORDER_TELEGRAM_CHAT_ID are optional; preserve them if intentionally using a separate order bot/chat.
4. Check /api/health: releaseId must be 2026-09-09.1.
5. Verify with a fresh browser session: open a public page, click/tap or use the mouse wheel, keep it visible for at least 35 seconds. A visit already notified within the dedupe window will not notify again.
6. Verify order and top-up flows with your own test account after deployment, including payment proof and admin review.

No new database migration is required by this patch. Follow the repository's normal deployment/migration procedure.

## Validation

Passed backend TypeScript build, frontend type check, production frontend build, and 5 focused tests covering bot blocking, engagement/path filtering, concurrent dedupe, main bot fallback, and top-up approval content. Telegram and database responses were mocked for focused tests. No live messages were sent, no live payments or balances were changed, and this ZIP has not been deployed.

Telegram delivery remains best-effort, as in the base build: errors are logged, but there is no durable retry queue across restarts.
