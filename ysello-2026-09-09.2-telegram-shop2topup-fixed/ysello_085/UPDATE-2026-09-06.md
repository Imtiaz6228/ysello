## Catalog, categories, pagination and SEO

- Public categories are no longer restricted to a hard-coded taxonomy list. Any active admin-created category can surface when it contains published products.
- Parent category product counts now include products in descendant categories. This prevents a parent from disappearing simply because products were assigned to child categories.
- Category pages use the selected category plus its descendants when loading products.
- Catalog pagination remains server-backed at 50 products per page. Out-of-range page URLs are normalized to the valid server-returned page.
- Server-rendered crawler navigation and the XML sitemap now retain stocked parent categories as well as leaf categories.
- Homepage/catalog titles and descriptions explicitly describe digital products, accounts, game top-ups, gift cards and subscriptions.
- WebSite/SearchAction structured data is present on the homepage for marketplace search discovery.

## SHOP2TOPUP reseller API

The integration is backend-only. No reseller credential is included in this ZIP.

Railway/API environment variables:

```env
SHOP2TOPUP_API_KEY=<set the credential in Railway, not in source>
SHOP2TOPUP_API_BASE_URL=https://shop2topup.com/api/endpoints/v1
SHOP2TOPUP_TIMEOUT_MS=15000
SHOP2TOPUP_MARGIN_PERCENT=20
SHOP2TOPUP_WEBHOOK_SECRET=<add after webhook registration/rotation in the supplier panel>
```

Admin endpoints added under `/api/admin/shop2topup`:

- `GET /status`
- `POST /test`
- `GET /catalog/big-categories`
- `GET /catalog/categories?bigCategoryId=...`
- `GET /catalog/subcategories?categoryId=...`
- `GET /catalog/subcategories/:itemId/price`
- `GET /catalog/categories/:categoryId/requirements`

The client also contains server-side player validation, order creation and order-status functions, but the admin catalog connection does **not** automatically publish or charge buyer-facing SHOP2TOPUP items. That avoids selling a player-ID-dependent top-up before the buyer requirements/settlement workflow is explicitly attached to a local product.

### Webhook

Public route:

```text
POST /api/webhooks/shop2topup
```

With the canonical production API origin, the expected URL is:

```text
https://api.ysello.com/api/webhooks/shop2topup
```

The handler is mounted before JSON parsing and CSRF middleware so it can verify the exact raw request body. Before a webhook secret is configured it is ACK-only and returns HTTP 204, allowing the supplier's HTTPS URL validation POST to succeed without performing any order action. After `SHOP2TOPUP_WEBHOOK_SECRET` is configured, it requires the signed HMAC-SHA256 callback and returns 401 for a bad signature.

The Admin → Suppliers workspace shows connection status, wallet/account health, markup, catalog groups, the exact deployment-derived webhook URL, settings/documentation links, and a connection-test button. It never displays the API secret.
